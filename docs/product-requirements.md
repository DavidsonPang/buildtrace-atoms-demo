# BuildTrace 产品需求文档

> 状态：D2 已确认（2026-09-07）  
> 产品方向：A+——默认快速推进、按需透明  
> 调研依据：[product-discovery.md](./product-discovery.md)  
> 范围：最小可用且有吸引力的产品；具体实现见技术设计文档。

## 1. 产品定义

**BuildTrace 通过一套快速、可观察的 AI 团队工作流，把商业想法转化为可运行的微型产品。**

它不同于不透明的“对话生成代码”：BuildTrace 会展示当前由哪个专业 Agent 执行、产生了什么产物、哪里失败，以及需求修改后哪些内容需要重建。它也不同于文档驱动的冗长流程：用户无需逐阶段审批即可尽快看到可运行结果。

### 目标用户

主要用户是独立创业者、运营人员或具备产品意识的构建者。他们：

- 有商业或工作流想法，但没有完整规格；
- 希望尽快得到可操作的结果；
- 需要足够的过程信息来信任并纠正 AI；
- 不希望配置开发环境，也不应被要求提供 API Key。

### 核心用户任务

> 当我只有一个不完整的产品想法时，请帮我快速生成一个可运行、可验证的微型产品，同时允许我查看和纠正重要产品决策，而不必从零重来。

## 2. 产品原则

1. **默认快速推进**：普通阶段自动执行，优先得到第一个预览。
2. **按需透明**：中间产物默认显示摘要，用户可以展开查看。
3. **真实工作，不做 Agent 剧场**：每个可见阶段都对应真实操作或确定性检查。
4. **在重要节点保留人工控制**：用户可编辑 Product Brief，并主动重建受影响内容。
5. **保留最近成功结果**：重建失败不能破坏上一个可用预览。
6. **诚实表达能力边界**：预置结果和实时生成必须标注，未实现的生产能力不得伪装为真实能力。
7. **调研必须有证据**：没有来源检索时使用 Idea Analysis，而不是 Research。

## 3. 核心场景

### 场景一：从模糊想法得到第一个结果

自由职业设计师输入“为客户创建项目报价计算器”。BuildTrace 分析用户与场景，生成 Product Brief 和 Technical Plan，构建交互式计算器并完成验证，无需等待逐阶段批准即可打开预览。

### 场景二：检查并纠正产品假设

用户打开 Product Brief，发现其中没有考虑加急交付。他加入加急系数并保存。BuildTrace 将 Technical Plan、Build 和 Validation 标记为过期，在用户确认后只重建这些下游内容。

### 场景三：从生成失败中恢复

模型返回格式错误或请求超时。BuildTrace 明确指出失败阶段和错误类型，保留已完成的上游产物与最近成功预览，并允许用户只重试失败阶段。

### 场景四：用自然语言继续修改成功版本

用户在成功预览下输入“保留现有报价流程，增加税费说明，并把结果卡片改成深色”。BuildTrace 将修改要求与当前 Product Brief 合并，重新执行完整 Pipeline，验证通过后生成新版本；用户仍可切回旧版本，并能在 Code 标签中分别检查 HTML、CSS 和 JavaScript。

## 4. 用户流程

### 4.1 快速模式——默认模式

```text
输入想法或选择示例
        ↓
开始生成
        ↓
Idea Analysis + Product Brief
        ↓ 自动推进
Technical Plan
        ↓ 自动推进
Build
        ↓ 自动推进
确定性 Validation
        ↓
可运行预览 + 可编辑产物
```

行为要求：

- 从一个自然语言输入开始；
- 请求被接受后立即展示真实阶段进度；
- 普通中间产物不阻塞后续生成；
- 后续阶段运行时，已完成产物仍可展开查看；
- 有效构建完成后自动切换到 Preview。

### 4.2 引导模式——可选模式

```text
描述想法、用户、核心操作和约束
        ↓
生成 Product Brief
        ↓
用户查看或编辑这一项高影响产物
        ↓ 用户主动点击“开始构建”
Technical Plan → Build → Validation → Preview
```

行为要求：

- 生成前可补充目标用户、核心操作和约束；
- 因用户主动选择更强控制，仅在 Product Brief 暂停一次；
- 用户开始构建后，其余阶段自动推进；
- 与快速模式共用产物、预览、验证和恢复机制。

### 4.3 编辑并重建

```text
打开已成功的 Product Brief
        ↓
编辑并保存新修订
        ↓
展示受影响的下游阶段
        ↓ 用户确认重建
将下游产物标记为 stale
        ↓
重新执行 Technical Plan → Build → Validation
        ↓
产生新版本，同时保留上一成功版本
```

### 4.4 自然语言迭代

```text
打开一个成功版本
        ↓
输入本轮修改要求
        ↓
合并当前 Product Brief 与修改要求
        ↓
重新执行 Product → Architecture → Engineering → Validation
        ↓
预览握手成功后提交新版本
```

自然语言迭代与结构化 Brief 编辑解决不同问题：前者适合快速表达文字、样式和功能调整，后者适合精确检查产品定义。首版不把上一版 HTML 发送给模型，而是基于原始想法、当前 Product Brief 和本轮修改要求完整重建，以限制上下文与费用；因此它不承诺像代码补丁一样只改一个字符。

## 5. 信息架构

核心体验集中在一个工作台：

- **左侧栏**：阶段导航和最近成功版本；
- **中间工作区**：需求输入、Agent 状态和可展开产物；
- **右侧检查器**：Preview、Code、Logs 和 Validation。

窄屏下，右侧检查器变为当前阶段下方的全宽标签页。首版不实现复杂项目管理和多项目导航。

## 6. 范围

### 6.1 Must——必须完成

#### M1. 通过快速或引导模式创建项目

- 空状态说明产品价值并展示两种模式；
- 快速模式接收一段自然语言想法；
- 引导模式额外提供目标用户、核心操作、约束，字段均可选；
- 三个一键示例可填入完整提示词；
- 空输入、超长输入或非法输入必须在模型调用前拒绝。

**验收标准：** 新用户选择示例后不超过两次操作即可启动快速模式；引导模式可在查看结构化上下文后开始。

#### M2. 执行并展示真实的分阶段 Agent Pipeline

- Pipeline 包含 Product、Architecture、Engineering、Validation 四类职责；
- UI 状态必须由真实请求事件驱动，不能用计时器伪造进度；
- 用户可以区分 queued、running、completed、failed、stale、cancelled 和 ready；
- 每个成功阶段记录 Agent、耗时、产物摘要和版本。

**验收标准：** 成功、失败、取消、重试和重建场景下，事件日志与阶段 UI 状态保持一致。

#### M3. 生成可检查的结构化产物

- Product 阶段生成 Idea Analysis 和 Product Brief；
- Architecture 阶段生成受限的 Technical Plan；
- 产物默认折叠为摘要，后续阶段运行时仍可查看；
- Product Brief 可按结构化字段编辑，而不是只能编辑大段文本。

**验收标准：** 每次成功运行都能查看目标用户、问题、核心操作、功能要求、约束和实际采用的实现概要。

#### M4. 生成可运行的自包含微型产品

- Engineering 阶段生成一份包含 HTML、CSS 和 JavaScript 的完整 HTML 文档；
- 结果至少实现一个有意义的用户交互，不能只是静态落地页；
- 生成代码不能依赖安装包、远程后端、密钥或外部运行时资源；
- 实时生成与预置示例必须明确标注。

**验收标准：** 五个固定冒烟提示词中至少四个无需人工修改代码即可产生可见且可交互的预览。

#### M5. 预览、检查并验证结果

- Preview 在受限 iframe 中运行，不能导航父页面或访问父应用；
- 同一工作台提供 Preview、Code、Logs 和 Validation；
- 确定性检查覆盖响应 Schema、文档大小、HTML 结构、禁止能力、可见内容、预览就绪和交互行为；
- 验证结果区分 pass、warning、failure，并尽可能关联对应需求。

**验收标准：** 无效或违反安全规则的结果不能进入预览；有效结果能上报就绪；运行时错误会显示在 Logs 和 Validation 中。

#### M6. 编辑 Product Brief 并重建下游内容

- 保存 Product Brief 修改时创建新修订；
- Technical Plan、Build、Validation 标记为 stale，Idea Analysis 保持不变；
- 确认前向用户展示重建影响；
- 成功重建后产生新版本，且结果发生与修改相符的变化。

**验收标准：** 修改一项功能要求后会产生新的 Technical Plan 和预览；在新版本成功前，上一个成功预览仍可使用。

#### M7. 明确处理失败、取消和重试

- 模型阶段运行时可以取消；
- 超时、结构化输出无效、Provider 拒绝、安全拒绝和预览运行错误使用不同提示；
- 重试从失败阶段继续，并复用有效上游产物；
- 如果启用自动修复，次数必须受限并在日志中说明。

**验收标准：** 在每个模型阶段注入失败时，流程都会进入可恢复的 failed 状态，而不是无限加载或显示空白预览。

#### M8. 保存有用状态并保护公共体验

- 同一浏览器刷新后恢复最近项目、产物、版本和最近成功预览；
- 存储结构有版本且容量受限，数据损坏时安全降级；
- 强制限制提示词长度、输出大小、请求时长、重试次数和生成频率；
- 实时生成不可用时，提供明确标记的预置项目，不能伪装为缓存的实时结果；
- 访问者无需提供 Provider Key，客户端代码也不能包含 Key。

**验收标准：** 成功和失败状态均可在刷新后恢复；客户端产物不包含 Provider Key；超限请求在调用模型前失败。

#### M9. 注册登录与本地优先云同步（D5 后范围升级）

- 用户可通过邮箱和密码注册、登录、恢复会话与退出；
- 配置 Supabase 的在线环境只允许已登录用户发起实时生成，预置项目仍可匿名体验；
- Supabase Postgres 保存用户项目元数据、Agent 结构化产物、最近三个成功版本和首版自包含 HTML；
- 浏览器继续保存按用户隔离的版本化快照，断网或云端失败不阻断本地编辑与恢复；
- 登录时比较该用户本地快照与云端快照的 `savedAt`，选择较新版本；仅在两者都为空时迁入游客项目，并重新生成项目/版本 ID；
- 数据库必须启用 RLS，匿名角色没有表权限，认证用户只能访问 `auth.uid()` 对应的数据；
- 单份 HTML 在 Postgres 中限制为 150 KB，超过首版边界后迁移到 Supabase Storage，而不是无限扩大行数据。

**验收标准：** 会话刷新后可恢复；不同账号的本地缓存和数据库行相互隔离；无效或缺失的 Bearer Token 不能调用在线生成；云端不可用时明确显示状态且本地快照仍可恢复；网络恢复后允许重新同步。

#### M10. 通过自然语言继续迭代成功版本

- 只有存在成功版本时才展示后续修改入口，修改要求限制为 3–800 字符；
- 修改请求必须携带当前 Product Brief，服务端重新校验后完整执行四阶段 Pipeline；
- 引导模式的后续迭代不再次停在 Product Brief，以避免重复阻塞；
- 新版本在确定性验证和 Preview Ready 握手前不得替换当前成功版本；
- 每个成功版本保存本轮修改要求，失败阶段重试继续复用同一要求；
- 为控制 Token 与费用，首版不把上一版完整 HTML 放入模型上下文。

**验收标准：** 对成功版本输入一条文字或功能修改要求后产生新版本，预览明确体现修改；运行期间和失败时旧版本仍可使用，版本列表可切回上一结果。

#### M11. 在 Code 标签中提供虚拟多文件预览

- 将通过验证的自包含 HTML 确定性投影为 `index.html`、`styles.css`、`app.js` 三个只读视图；
- 文件列表可切换，并显示语言和行数；多个内联 Style/Script 块按原顺序合并；
- 界面必须明确标注“虚拟文件视图”，不能暗示后台已生成真实多文件仓库；
- 运行、下载、验证和持久化仍以同一份自包含 HTML 为唯一事实来源。

**验收标准：** 成功版本可以在三个文件间切换，HTML 视图使用虚拟引用替代内联块，CSS/JavaScript 视图包含原始内容，预览行为不受投影影响。

### 6.2 Should——时间允许时完成

- 设备宽度预览控制；
- 并排或文本形式的版本 Diff；
- 回滚到历史成功版本；
- 下载生成的 HTML；
- 生成前润色提示词；
- 对无效模型输出执行一次受限自动修复；
- 工作台快捷键和更完整的窄屏体验。

### 6.3 Won't——升级版仍明确不做

- 团队空间、角色权限、邀请、共享项目或审计后台；
- 多项目列表、项目搜索和复杂冲突合并；首版只恢复该用户最近项目并采用 Last-Write-Wins；
- Supabase Storage Artifact 迁移；当前 HTML 仍受 150 KB 数据库上限保护；
- 真实多文件仓库、写回源码或动态安装 npm 依赖；Code 标签只提供自包含 HTML 的只读虚拟投影；
- 生成应用的真实后端、数据库、鉴权、支付或部署；
- 在服务端运行不受信任的生成代码；
- 通用可视化/WYSIWYG 页面编辑器；
- 在没有来源检索能力时声称进行真实 Web Research；
- SEO、广告投放、分析编排、自定义域名或一键发布生成应用；
- 原生移动应用生成。

## 7. 演示用例

### 7.1 自由职业者项目报价计算器

- **用户**：自由职业设计师或开发者；
- **核心操作**：输入服务、工时、时薪、加急程度和附加服务；
- **结果**：分项报价、总价、交付时间和可复制的客户摘要；
- **价值**：商业价值明确，计算结果可确定性验证。

### 7.2 活动报名与容量看板

- **用户**：小型活动组织者；
- **核心操作**：添加报名人员并跟踪剩余名额；
- **结果**：容量状态、报名列表、候补逻辑和筛选；
- **价值**：展示本地状态、表单、状态转换和运营价值。

### 7.3 SaaS 定价与 ROI 计算器

- **用户**：小型 SaaS 创业者或采购者；
- **核心操作**：比较套餐，输入团队人数、人力成本和预计节省时间；
- **结果**：套餐建议、每月节省金额、回本周期和 CTA；
- **价值**：把交互工具与购买决策联系起来。

## 8. 五个固定冒烟提示词

开发与最终验证统一复用以下提示词：

1. **中文 / 计算器**：“为自由职业设计师创建一个项目报价计算器。用户可以选择服务、填写预计工时和时薪、设置加急程度和附加服务，然后看到分项报价、总价、交付时间，并复制一段客户报价摘要。”
2. **英文 / 本地状态**：“Build an event registration and capacity board for a 30-person workshop. Let the organizer add attendees, move overflow registrations to a waitlist, filter by status, and see remaining seats.”
3. **中文 / 商业决策**：“创建一个小型 SaaS 的定价和 ROI 计算器，根据团队人数、人工成本、每周节省时间推荐套餐，并计算月度节省金额和回本周期。”
4. **英文 / 模糊输入**：“Create a useful lead qualification tool for a small B2B design agency. Make reasonable assumptions, explain them in the Product Brief, and build an interactive result.”
5. **中文 / 多种交互**：“为社区咖啡店制作一个团购预订工具，可以选择商品和数量、计算阶梯折扣、显示取货时间、保存当前订单，并生成可复制的取货摘要。”

## 9. 成功标准

### 核心体验

- 首次访问者能在 30 秒内理解产品并启动一个示例；
- 请求被接受后立即出现真实进度；
- 五个固定提示词中至少四个通过 Schema、沙箱、就绪、可见内容和交互检查；
- 失败流程不会无限停留在 loading；
- 编辑 Product Brief 后产生可追踪的新版本和可见的下游变化。
- 自然语言修改后产生可回滚的新版本，且代码面板可分别检查 HTML、CSS 和 JavaScript。

### 稳定性与信任

- 重建失败和浏览器刷新都不会丢失最近成功预览；
- 每个显示的阶段都对应真实操作或确定性验证器；
- 每个错误都指出失败阶段和下一步操作；
- 预置项目、实时模型结果、警告和未经验证的 LLM 判断在视觉上可区分。

### 无障碍基线

- 主要控件可通过键盘访问并具有可读名称；
- 状态不能只通过颜色传达；
- 加载和错误变化通过合适的 live region 告知辅助技术。

## 10. 主要风险与降级方案

| 风险                       | 影响                   | 首选缓解方式                                | 降级方案                                                      |
| -------------------------- | ---------------------- | ------------------------------------------- | ------------------------------------------------------------- |
| 多阶段延迟导致预览过慢     | 第一印象差             | 精简阶段 Prompt、限制输出、立即展示真实进度 | 合并 Idea Analysis 和 Product Brief 为一次 Product Agent 调用 |
| 模型输出格式错误           | 后续无法执行           | 严格 Schema + 一次受限修复                  | 明确阶段错误并允许手动重试                                    |
| 生成 HTML 不安全或无法运行 | 安全风险或空白预览     | 结构检查、CSP、受限 iframe、运行时握手      | 阻止预览并保留最近成功版本                                    |
| 下游重建过于复杂           | 差异化能力不稳定       | 使用固定的 Product Brief 下游依赖链         | 从 Product Brief 开始完整重建，但保留版本                     |
| 公共生成额度耗尽           | 访问者无法完成实时生成 | 严格限制、Provider 预算、明确可用状态       | 提供完整且明确标注的预置项目                                  |
| 浏览器存储超限或损坏       | 刷新恢复失败           | 限制版本数量、Schema 迁移                   | 只保留最近成功版本或允许本地重置                              |

## 11. D2 之后仍需决策的事项

产品范围不依赖某个具体模型或部署平台，以下外部选择仍由后续门禁控制：

- **D3**：模型供应商、模型、服务端凭证、预计用量和费用上限；
- **D4**：部署平台、项目标识、环境变量和远程资源创建；
- **D5**：公开仓库名称、License、可见性和允许推送的 Git 历史。

在对应决策确认前，不接入真实模型、不创建远程部署，也不创建公开仓库。
