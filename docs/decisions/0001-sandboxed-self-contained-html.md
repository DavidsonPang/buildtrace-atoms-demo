# ADR-0001：生成沙箱化的自包含 HTML

- **状态**：已接受（2026-09-07）
- **日期**：2026-09-06
- **决策责任**：产品与工程

## 背景

BuildTrace 需要把一个想法转化为可运行、可交互的预览，同时必须把模型生成代码视为不受信任输入。

通用应用生成器可以生成多文件 React 项目、安装依赖、执行构建，甚至运行生成的服务端代码。但这会在核心产品闭环得到验证前，引入包安装、构建工具差异、服务端代码执行、长等待时间和更复杂的隔离边界。

首版真正需要证明的是：

- Agent 分阶段工作真实发生；
- 最终结果具有实际交互；
- 验证规则可以确定性执行；
- 错误可见且能够恢复；
- 本地和线上预览行为稳定。

## 决策

Engineering Agent 只生成一份包含内联 CSS 和 JavaScript 的完整 HTML 文档。

应用必须：

- 拒绝超过大小和结构限制的输出；
- 解析并检查文档后才允许运行；
- 拒绝远程依赖以及被禁止的元素和能力；
- 注入严格 CSP 和带作用域的 Runtime Reporting Bridge；
- 使用 `iframe srcDoc` 和 `sandbox="allow-scripts"` 渲染，且不加入 `allow-same-origin`；
- 只接受来自当前 Frame 且带有 Run Channel Token 的 Preview 消息；
- 永远不在服务端执行生成代码。

## 影响

### 正面影响

- 不需要动态安装依赖，也不需要运行生成项目的构建流程；
- Preview 启动快速且可预测；
- 结果可以作为单一 Artifact 检查、下载、保存版本和复现；
- 生成代码运行环境与父应用隔离；
- 验证器可以围绕一个受限文档契约工作。

### 负面影响

- 生成应用不能拥有真实后端、鉴权、支付或服务端持久化；
- 无法通过生成结果展示框架级组件结构；
- 隔离文档中的内联脚本和样式需要对应 CSP 例外；
- iframe Sandbox 能降低风险，但不等价于独立域名和独立运行环境；
- 复杂应用在单文档中的可维护性和质量存在上限。

## 被考虑的替代方案

### 在浏览器生成 React/Vite 仓库

首版不采用。虚拟文件系统、依赖解析、构建启动和 iframe 托管会增加大量失败点，而对核心 Agent 产品决策的证明价值有限。

### 在服务端构建生成仓库

不采用。运行不受信任的构建脚本需要容器隔离、资源配额、网络控制、Artifact 存储、清理和滥用防护。只实现其中一部分会造成误导性的安全承诺。

### 直接把生成内容渲染进父页面 DOM

不采用。这样会让不受信任内容接触父应用的凭证、DOM、存储、导航和事件系统。

### 只生成不含 JavaScript 的静态 HTML

不采用。核心结果必须展示有意义的用户交互，而不只是视觉页面生成。

## 生产演进

如果产品证据支持更通用的生成能力，应将 Build 和 Preview 迁移到独立 Origin 及隔离 Worker/Container。项目 Manifest 需要声明文件、Runtime、依赖、权限和资源限制；构建产物经过扫描后不可变存储，并由受限 Preview Domain 提供。

当前的 `GeneratedApp` 和 `PreviewRuntime` 接口应隐藏底层实现，使未来替换运行时边界时不影响工作台 UI。

## 决策验证条件

只有早期测试证明以下条件时，本决策才继续有效：

- 三个演示场景在单文档中都能实现有意义交互；
- CSP 和 iframe 策略在支持目标交互的同时阻止网络和父页面访问；
- ready、error 和 interaction 消息能准确归属当前 Run；
- 非法或禁止输出会在进入 Preview 前被拦截；
- 托管环境在目标浏览器中稳定渲染 `srcdoc`。

如果验证失败，不能通过静默放宽 Sandbox 来绕过。必须重新评估运行时边界，并新增替代 ADR。
