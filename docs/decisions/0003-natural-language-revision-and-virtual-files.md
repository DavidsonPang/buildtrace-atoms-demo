# ADR-0003：基于 Product Brief 重建并提供虚拟多文件视图

- 状态：已接受
- 日期：2026-09-07
- 关联需求：M10、M11

## 背景

成功生成首版后，用户需要继续修改文案、样式或功能；评审者也希望比单个长 HTML 更容易检查生成源码。但当前安全与运行边界刻意限定为一份自包含 HTML：它无需安装依赖、可以确定性校验，并能直接进入受限 iframe。

这里有两个容易混淆的问题：怎样让修改后的产品、架构和实现保持一致，以及怎样改善源码阅读体验。它们不要求立即引入真实多文件构建系统。

## 决策

### 自然语言修改

- 客户端提交原始产品想法、当前已验证 Product Brief 和本轮修改要求；
- Product、Architecture、Engineering、Validation 四阶段完整重跑；
- 上一版 HTML 不进入模型上下文，避免请求体与 Token 随版本体积增长；
- 修改过程不覆盖当前成功预览；确定性验证和 Preview Ready 均通过后才提交新版本；
- 每个版本保存本轮修改要求，失败阶段重试沿用同一要求。

### 源码查看

- 只有成功版本的 `generatedApp.html` 及其经验证、注入后的 `acceptedHtml` 才能进入版本记录；
- Code 面板从活动成功版本的原始 `generatedApp.html` 确定性提取内联 Style 与 Script，并展示 `index.html`、`styles.css`、`app.js`；
- UI 明确标记“虚拟文件视图”，该结果只读，不代表真实仓库或构建产物；
- 多个同类型代码块按原顺序合并并标记来源。

## 备选方案

### 把上一版 HTML 交给模型生成补丁

优点是可能更接近局部修改；缺点是上下文大、补丁应用与冲突处理复杂，而且 Product Brief、Technical Plan 可能和代码漂移。当前不采用。

### 直接升级为真实多文件项目

需要文件协议、依赖解析、构建沙箱、Artifact 存储和更强供应链隔离，显著扩大原型攻击面与失败面。当前不采用。

### 只保留结构化 Brief 编辑

实现简单但不能覆盖用户自然表达文案和视觉修改的主要习惯，也削弱连续构建体验。当前不采用。

## 结果

收益：用户能快速连续迭代，旧版本始终可恢复；评审者能分别阅读结构、样式和行为代码；运行链路仍保持一个可审计事实来源。

代价：自然语言修改是语义重建而非逐字符补丁，未提及的视觉细节可能变化；虚拟文件不能编辑、下载为项目或安装依赖。需要这些能力时，应迁移到隔离 Build Service、真实文件 Manifest 和 Artifact Registry。
